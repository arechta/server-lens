# pipeline — Stage Architecture & Data Handoff

> Sub-document of `server-lens`. Referenced from `@AGENTS.md`.
> Covers: the full DevOps pipeline stage map, scan scheduling, SSH welcome screen
> integration, downstream tool data consumption, and inter-stage handoff contract.

---

## Overview

`server-lens` is Stage 1 of a multi-stage DevOps automation pipeline. Its output —
`state.json` and `server-lens.db` — is the **shared state** all subsequent stages read.
No stage re-scans the system. No stage re-fetches upstream version data.
One scan, consumed by all.

```
┌─────────────────────────────────────────────────────────────────┐
│                        PIPELINE OVERVIEW                        │
├──────────┬──────────────────────────────────────────────────────┤
│ Stage 1  │ server-lens scan                                     │
│          │ Snapshot system state → state.json + server-lens.db  │
├──────────┼──────────────────────────────────────────────────────┤
│ Stage 2  │ service-stopper                                      │
│          │ Stop systemd units + PM2 processes before updates    │
├──────────┼──────────────────────────────────────────────────────┤
│ Stage 3  │ os-updater                                           │
│          │ apt update + apt full-upgrade                        │
├──────────┼──────────────────────────────────────────────────────┤
│ Stage 4  │ runtime-updater                                      │
│          │ nvm, node, npm globals, pnpm globals, bun            │
├──────────┼──────────────────────────────────────────────────────┤
│ Stage N  │ container-updater (planned)                         │
│          │ docker compose pull + recreate per service           │
├──────────┼──────────────────────────────────────────────────────┤
│ Stage N  │ service-restarter (planned)                         │
│          │ Restart everything stopped in Stage 2               │
└──────────┴──────────────────────────────────────────────────────┘
```

## Stage 1: `server-lens scan`

### What it does
- Runs all auto-discovery scanners
- Runs all registered probes from `server-lens.toml`
- Diffs results against last SQLite snapshot
- Emits events for all detected changes
- Fires configured webhooks
- Writes updated state to `server-lens.db`
- Outputs `state.json` if `--json` flag is passed

### When it runs
Triggered by cron or systemd timer — schedule defined in `server-lens.toml` under
`[settings].scan_schedule` as a cron expression. No hardcoded default.

### Handoff to downstream stages
```bash
# Run scan and save output for pipeline
server-lens scan --json > /tmp/state.json

# All subsequent stages read this file
# File persists for the duration of the pipeline run
# Delete after pipeline completes or keep for audit
```

### Display mode (separate from scan)
```bash
# SSH welcome screen — instant, reads SQLite, zero network
server-lens

# Force fresh scan then display
server-lens scan --now
```

## Scheduling: Cron vs systemd Timer

Two options for scheduling the background scan — both work, choose one per server.

### Option A: `/etc/cron.d/server-lens` (simpler)
```cron
# Schedule defined in server-lens.toml [settings].scan_schedule
# This file is generated by `server-lens install` using that cron expression
# Example: every 6 hours
0 */6 * * * root /usr/local/bin/server-lens scan --quiet 2>&1 | logger -t server-lens
```

### Option B: systemd timer (more observable)
```ini
# /etc/systemd/system/server-lens.timer
[Unit]
Description=server-lens scheduled scan
After=network-online.target

[Timer]
OnCalendar=*-*-* 00,06,12,18:00:00
Persistent=true

[Install]
WantedBy=timers.target
```
```ini
# /etc/systemd/system/server-lens.service
[Unit]
Description=server-lens scan
After=network-online.target

[Service]
Type=oneshot
ExecStart=/usr/local/bin/server-lens scan --quiet
User=root
```

The systemd timer approach gives you `systemctl status server-lens.timer`,
journald logs, and `Persistent=true` so a missed scan (server was off) runs
on next boot. Recommended for production EC2 instances.

## SSH Welcome Screen / MOTD Integration

`server-lens` (display mode) is safe for MOTD — instant render from SQLite, no network.

```bash
# /etc/update-motd.d/99-server-lens
#!/bin/bash
exec /usr/local/bin/server-lens
```

```bash
chmod +x /etc/update-motd.d/99-server-lens
```

Display mode shows:
- Last scan timestamp and next scheduled scan (`server-lens status` info inline)
- Outdated tool count by category
- Any `system.reboot_required` or `system.service_degraded` alerts
- Probe failure warnings if last scan had errors

If no scan has run yet (fresh install), display mode shows a prompt to run
`server-lens scan --now` rather than an empty or broken state.

## `server-lens status` Subcommand

Shows the health and schedule state of `server-lens` itself — not tool versions.

Output includes:
- Last scan: timestamp + duration + tool count + probe success/fail count
- Scan status: `completed` | `partial` | `failed`
- Next scheduled scan: computed from `scan_schedule` cron expression in TOML
- Recent events: last 5 events from the event log (summary, not full detail)
- Webhook delivery health: last N webhook attempts, success rate

Useful as a quick sanity check when SSH-ing in:
```
server-lens status

  Last scan:    2025-03-14 06:00:01  (completed, 42 tools, 12.3s)
  Next scan:    2025-03-14 12:00:00  (in 5h 47m)
  Outdated:     7 tools  (1 major, 3 minor, 3 patch)
  Probe issues: 2 failed, 0 rate-limited
  Webhooks:     last 10/10 delivered successfully
  Alerts:       ⚠ system.reboot_required detected
```

## Stage 2: `service-stopper`

### Input from state.json
```bash
# All services that need to be stopped before updates
jq '.tools[] | select(.category == "systemd" or .category == "pm2")' state.json

# systemd units only
jq '.tools[] | select(.category == "systemd") | .name' state.json

# PM2 processes only
jq '.tools[] | select(.category == "pm2") | .name' state.json
```

### Default behaviour
The service stopper reads a **chosen default list** from its own config — it does not
blindly stop everything in state.json. The operator pre-configures which services
are safe to stop for maintenance. state.json is used to verify those services exist
and are currently active before attempting to stop them.

### Handoff
Writes a `stopped-services.json` — list of what was actually stopped successfully.
Stage N (service-restarter) reads this to know exactly what to bring back up,
avoiding restarting services that were already stopped before the pipeline began.

## Stage 3: `os-updater`

### Input from state.json
```bash
# Check if OS-level updates are needed
jq '.tools[] | select((.category == "os" or .category == "apt") and .is_outdated == true)' state.json
```

### What it runs
```bash
apt-get update
apt-get full-upgrade -y
apt-get autoremove -y
```

### Guards
- Checks `state.json` summary — if `by_category.apt == 0` outdated, skips entirely
- After upgrade, checks `/var/run/reboot-required` — emits `system.reboot_required` event
  and notifies operator rather than auto-rebooting

---

## Stage 4: `runtime-updater`

### Input from state.json
```bash
# Runtime tools needing update
jq '.tools[] | select(.category == "runtime" and .is_outdated == true)' state.json
```

### What it handles

| Tool | Update method |
|---|---|
| nvm | `curl` install script (same as original install) — updates nvm itself |
| Node.js (nvm-managed) | `nvm install --lts` + `nvm alias default lts/*` |
| Node.js (system) | Handled by Stage 3 apt updater if installed via apt |
| npm | `npm install -g npm@latest` |
| pnpm globals | `pnpm update -g` |
| npm globals (pm2, etc.) | `npm update -g <package>` per outdated package |
| Bun | `bun upgrade` |

### Guards
- Major version updates (`update_type == "major"`) are flagged for human review —
  not auto-updated. Operator receives webhook notification and must manually approve.
- `update_type == "patch"` and `"minor"` proceed automatically.

---

## Stage N: `container-updater` (planned)

### Input from state.json
```bash
jq '.tools[] | select(.category == "container" and .is_outdated == true) | .name' state.json
```

### What it will do
Per outdated container service, in the service's Docker Compose directory:
```bash
docker compose pull
docker compose up -d --remove-orphans
```

Service directories follow the established pattern:
`/var/www/docker/<service-name>/docker-compose.yml`

## Inter-Stage Data Handoff Contract

All stages communicate through files in a shared pipeline working directory
(e.g. `/tmp/server-lens-pipeline-<timestamp>/`):

| File | Written by | Read by | Contents |
|---|---|---|---|
| `state.json` | Stage 1 | All stages | Full VersionEntry array — the shared source of truth |
| `stopped-services.json` | Stage 2 | Stage N (restarter) | List of services stopped successfully |
| `update-log.json` | Stages 3, 4, N | Reporting / webhook | What was updated, before/after versions, errors |
| `pipeline-meta.json` | Pipeline runner | All stages | Run ID, start time, operator, dry-run flag |

### `update-log.json` schema (per stage entry)
```typescript
interface UpdateLogEntry {
  stage:           number            // 2, 3, 4, N
  stage_name:      string            // "os-updater", "runtime-updater", etc.
  tool_name:       string
  category:        string
  version_before:  string | null
  version_after:   string | null
  success:         boolean
  error_message:   string | null
  duration_ms:     number
  updated_at:      string            // ISO 8601
}
```

## `server-lens serve` — HTTP API Server

### Starting the server

```bash
server-lens serve                  # Binds to host/port from [api] in server-lens.toml
server-lens serve --port 9000      # Override port at runtime
server-lens serve --host 0.0.0.0   # Override host at runtime (requires token in TOML)
```

The API server and the scan scheduler run in the same process.
The scheduler wakes on a tick, checks `schedules` table for due entries, and fires scans.

---

### TOML `[api]` Configuration Block

```toml
[api]
host  = "127.0.0.1"   # Bind address. 127.0.0.1 = localhost only (safe default)
                       # 0.0.0.0 = all interfaces (requires token)
                       # Specific IP = that interface only (requires token if non-localhost)
port  = 7845           # Custom port — no standard port conflicts
token = ""             # Bearer token. REQUIRED if host != "127.0.0.1"
                       # Leave empty for localhost-only deployments
```

**Auth guard rule:**
- `host = "127.0.0.1"` + no token → server starts, unauthenticated (localhost trust)
- `host != "127.0.0.1"` + no token → server **refuses to start**, logs clear error
- `host != "127.0.0.1"` + token set → server starts, all routes require `Authorization: Bearer <token>`

---

### Full Endpoint Reference

```
GET    /api/health                 Liveness check — server version, last scan time, scheduler state
GET    /api/tools                  All tools. Query: ?category= &outdated= &update_type= &probe_status= &status=
GET    /api/tools/:name            Single tool by name — full VersionEntry
GET    /api/snapshots              Scan history list — id, scanned_at, status, counts (no payload)
GET    /api/snapshots/:id          Single snapshot — full payload_json included
GET    /api/events                 Event log. Query: ?event= &since= &tool_name= &limit= (default 50)
POST   /api/scan                   Trigger scan now → 202 { job_id } or 409 if already running
GET    /api/scan/status            Current scan job state — queued | running | completed | failed
GET    /api/schedules              All schedule entries
POST   /api/schedules              Create schedule — body: { name, type, value, enabled }
PATCH  /api/schedules/:id          Update schedule — partial body: { name?, type?, value?, enabled? }
DELETE /api/schedules/:id          Delete schedule entry
GET    /api/webhooks/log           Webhook delivery history. Query: ?event= &success= &limit=
```

### Scan Trigger Flow (Async)

```
Client                         API Server                    Scan Engine
  │                                │                               │
  │  POST /api/scan                │                               │
  │ ─────────────────────────────► │                               │
  │                                │  Check: scan already running? │
  │                                │  No → create scan_jobs row    │
  │                                │  job_id = uuid, status=queued │
  │  202 { job_id }                │                               │
  │ ◄───────────────────────────── │                               │
  │                                │  Spawn async scan             │
  │                                │ ────────────────────────────► │
  │                                │  Update job: status=running   │
  │                                │                               │  ... scanning ...
  │  GET /api/scan/status          │                               │
  │ ─────────────────────────────► │                               │
  │  200 { status: "running" }     │                               │
  │ ◄───────────────────────────── │                               │
  │                                │                               │  scan complete
  │                                │  Update job: status=completed │
  │                                │  Write snapshot, emit events  │
  │                                │  Fire webhooks                │
  │  GET /api/scan/status          │                               │
  │ ─────────────────────────────► │                               │
  │  200 { status: "completed",    │                               │
  │        snapshot_id: 42 }       │                               │
  │ ◄───────────────────────────── │                               │
```

### Schedule Resolution Priority

On startup, the scheduler determines the active schedule set:

```
1. Load all rows from SQLite schedules table where enabled = 1
2. If table is empty:
     → Read [settings].scan_schedule from TOML
     → Seed one "cron" row into schedules table (created_by = "system")
     → Use that row going forward
3. If table has rows: TOML scan_schedule is ignored entirely
4. Scheduler ticks every minute, evaluates next_run_at for each enabled row
5. For one-time entries: after running, set enabled = 0 (not deleted — kept as history)
```

This means:
- First install with TOML cron → seeds SQLite → runs from SQLite forever after
- Add API schedule → both run on their own cadence independently
- Disable TOML-seeded schedule via API → `PATCH /api/schedules/1 { "enabled": false }` → no more background scans until re-enabled or new schedule created

### Accessing from Local Network / Team

To expose `server-lens serve` to your local network (e.g. team members, n8n, Outline):

```toml
[api]
host  = "0.0.0.0"
port  = 7845
token = "your-strong-secret-token"   # Required — server won't start without this
```

Then from another machine or tool:
```bash
curl -H "Authorization: Bearer your-strong-secret-token"      http://<server-ip>:7845/api/health
```

For n8n HTTP Request node, set:
- URL: `http://<server-ip>:7845/api/tools?outdated=true`
- Auth: Header — `Authorization: Bearer <token>`

## MCP Integration with `server-lens serve`

When `server-lens serve` starts, it exposes three interfaces on the same port:

```
http://host:port/api/*   → REST API (existing)
http://host:port/mcp     → MCP Server-Sent Events endpoint
server-lens mcp          → stdio transport (separate subcommand, no HTTP)
```

MCP is enabled by default when `[mcp].enabled = true` in TOML.
The `/mcp` endpoint uses the same Bearer token as `/api/*` — one auth config for both.

### Claude Code connecting to a remote server-lens

```json
{
  "mcpServers": {
    "server-lens-prod": {
      "type": "sse",
      "url": "http://your-ec2-ip:7845/mcp",
      "headers": { "Authorization": "Bearer your-token" }
    }
  }
}
```

Once connected, Claude Code can answer natural language questions like:
- *"What needs updating on the prod server?"* → calls `get_outdated`
- *"Run a scan now and tell me what changed"* → calls `scan_now`, polls `get_scan_status`, calls `get_events`
- *"Schedule a scan for tonight at 2am"* → calls `create_schedule`
- *"Are there any major version updates I should review?"* → calls `get_tools` with `update_type=major`

See `@docs/mcp.md` for the full MCP tool, resource, and prompt reference.

## Dry-Run Mode

All pipeline stages (including `server-lens scan`) support `--dry-run`:

```bash
server-lens scan --dry-run --json > state.json
```

In dry-run mode:
- All discovery and probing runs normally — full state.json produced
- No writes to SQLite
- No events emitted
- No webhooks fired
- Downstream stages receiving a dry-run `pipeline-meta.json` print what they *would* do
  without executing any system commands

Useful for validating probe coverage and pipeline logic before a real maintenance window.
