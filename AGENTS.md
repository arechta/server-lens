# server-lens — Agent Context

> AI agent entry point for the `server-lens` project.
> Read this file first. Sub-documents are referenced inline where relevant.

---

## What Is This Project?

`server-lens` is a compiled, standalone CLI binary (built with Bun) for Linux servers.
Its single responsibility: **snapshot the current state of a server** — every installed tool,
runtime, OS component, and self-hosted service — comparing current versions against
latest available versions upstream, and outputting structured data for both human
consumption and machine pipeline consumption.

It is **Stage 1** of a larger DevOps automation pipeline. It runs first. All subsequent
pipeline stages (service stopper, OS updater, runtime updater, etc.) consume its output.
It never performs updates itself.

---

## Two Sibling Concepts

| Concept | Role |
|---|---|
| `server-lens` | The CLI binary — scans, gathers versions, emits events, outputs snapshot |
| `upstream-probe` | The internal engine inside `server-lens` — fetches latest versions from upstream sources |

`upstream-probe` is not a separate binary. It is the probe subsystem of `server-lens`,
architected as a modular, extensible set of typed probes — one per upstream source type.
See `@docs/probe-engine.md` for full detail.

---

## Core Design Principles

- **Read-only.** `server-lens` never modifies the system. It only reads and queries.
- **Compiled binary.** No Node.js or Bun runtime required on the target server.
  The binary is self-contained. Deploy via `scp`, run directly.
- **Decoupled scan and display.** Scanning (network calls, apt queries) is expensive and
  runs on a schedule. Display reads the last SQLite snapshot instantly — suitable for
  SSH welcome screens and MOTD without any delay or API calls.
- **Single snapshot, multiple consumers.** Run once, save output, pass to all downstream stages.
  No re-scanning, no re-fetching across the pipeline.
- **Graceful unknowns.** If a tool cannot be probed for latest version, it still appears in
  output — marked `untracked`. Current version is always shown; latest is best-effort.
- **Event-driven.** Every scan diffs against the previous SQLite snapshot and emits
  structured events. Events can trigger webhook calls configured in `server-lens.toml`.
- **API-ready.** Architecture is designed to support a future `server-lens serve` subcommand
  exposing a REST HTTP API over the SQLite database — no structural changes needed.

## Tech Stack

| Layer | Choice | Reason |
|---|---|---|
| Language | TypeScript | Type safety for schema contracts and event payloads |
| Runtime / compiler | Bun | Native TS, fast compile, small self-contained binaries, built-in SQLite |

| MCP SDK | `@anthropic-ai/model-context-protocol` | MCP tools, resources, prompts — stdio + SSE transports |
| Target platforms | Linux x64, Linux arm64 | EC2 / VM servers (primary), macOS for local dev |

## Subcommands

| Subcommand | Speed | What it does |
|---|---|---|
| `server-lens` | ⚡ Instant | **Display mode** — reads last SQLite snapshot, renders TUI. Use for SSH welcome screen / MOTD. Zero network calls. |
| `server-lens scan` | 🐢 5–15s | **Scan mode** — runs all probes, queries upstreams, writes to SQLite, emits events, fires webhooks. Run via cron/systemd timer. |
| `server-lens scan --now` | 🐢 5–15s | Force fresh scan on demand, then display results. |
| `server-lens status` | ⚡ Instant | Shows last scan timestamp, next scheduled scan time (from TOML cron config), probe success/fail summary. |
| `server-lens events` | ⚡ Instant | Shows event log from SQLite — filterable by domain, severity, date range. |
| `server-lens --json` | ⚡ Instant | Outputs last snapshot as JSON to stdout — for pipeline consumption. |
| `server-lens --outdated` | ⚡ Instant | Display mode filtered to outdated tools only. |
| `server-lens --category <name>` | ⚡ Instant | Display mode filtered by category. |
| `server-lens serve` | — | **(Future)** Starts REST HTTP API server over SQLite. |

### SSH Welcome Screen / MOTD Integration
```bash
# /etc/update-motd.d/99-server-lens
#!/bin/bash
server-lens          # instant — reads SQLite, no network

# /etc/cron.d/server-lens  (schedule configured in server-lens.toml)
# Generated by server-lens install — cron expression comes from [settings].scan_schedule
```

Scan schedule is defined in `server-lens.toml` under `[settings].scan_schedule` as a
cron expression. There is no hardcoded default — the user sets it explicitly on install.
`server-lens status` always shows when the next scan is due based on that config.

## Storage Architecture

Two distinct storage layers — never mixed:

### `server-lens.toml` — Human configuration (static)
Location: `/etc/server-lens/server-lens.toml`
Purpose: Probe definitions (the interest list), webhook endpoints, global settings, API tokens.
Written by: Humans and agents. Version-controlled. Never written to by the tool at runtime.

### `[mcp]` block in `server-lens.toml` — MCP server config
Enables or disables the MCP server when running `server-lens serve`.
`server-lens mcp` (stdio) works regardless of this flag.
MCP inherits `[api].host`, `[api].port`, and `[api].token` — no separate config.
See `@docs/mcp.md` for full MCP spec.

### `[theme]` block in `server-lens.toml` — UI theme config
Defines the active color theme: `claude` (default, orange), `claude-blue`, or `custom`.
When `custom`, individual color tokens can be overridden per-token.
See `@docs/ui-design.md` for the full token reference and built-in theme palettes.

### `[api]` block in `server-lens.toml` — API server config
Defines bind address, port, and optional auth token.
`host = "127.0.0.1"` (localhost) requires no token.
`host = "0.0.0.0"` or any non-localhost value requires `token` to be set.

### `server-lens.db` — Persistent state (dynamic)
Location: `/var/lib/server-lens/server-lens.db`
Purpose: Discovery state, scan history, event log, webhook delivery log.
Written by: The tool at runtime on every scan. Never manually edited.

| Table | What it stores |
|---|---|
| `tools` | All discovered + registered tools, current version, probe status, last seen |
| `snapshots` | Full scan results per run — timestamped history |
| `events` | Structured event log — one row per event emitted |
| `webhooks_log` | Webhook delivery attempts, HTTP status codes, response bodies |
| `schedules` | Scan schedule entries — one-time and cron, managed via API or seeded from TOML |

See `@docs/data-schema.md` for full table schemas and field types.

## Events System

On every scan, `server-lens` diffs current results against the last snapshot in SQLite
and emits structured events. Events are stored in `server-lens.db` and optionally
delivered to configured webhook endpoints.

### Event Taxonomy

Events follow the pattern: `{domain}.{action_past_tense}`

| Domain | Events |
|---|---|
| `scan.*` | `scan.started`, `scan.completed`, `scan.failed`, `scan.partial` |
| `tool.*` | `tool.discovered`, `tool.removed`, `tool.untracked`, `tool.version_changed` |
| `version.*` | `version.outdated`, `version.up_to_date`, `version.major_available` |
| `probe.*` | `probe.failed`, `probe.timeout`, `probe.rate_limited`, `probe.undefined` |
| `config.*` | `config.loaded`, `config.invalid`, `config.probe_conflict` |
| `system.*` | `system.service_degraded`, `system.disk_warning`, `system.reboot_required` |

Every event payload carries: `event`, `timestamp` (ISO 8601), `severity`, `data` (event-specific object).
See `@docs/data-schema.md` for per-event `data` shapes.

### Webhook Delivery
Webhook endpoints are defined per event type in `server-lens.toml`.
On event emission, `server-lens` POSTs the event payload as JSON to each configured endpoint.
Delivery attempts (success or failure) are logged to the `webhooks_log` table in SQLite.
Failed webhook delivery must never block or fail a scan — log and continue.

## Pipeline Role

```
[server-lens scan] ──► server-lens.db  +  state.json (via --json)
                              │
                              ├──► Stage 2: service-stopper   (category: "systemd" | "pm2")
                              ├──► Stage 3: os-updater        (category: "os" | "apt")
                              ├──► Stage 4: runtime-updater   (category: "runtime")
                              ├──► Stage N: container-updater (category: "container")
                              └──► Stage N: ...               (same file, filtered)
```

Each downstream stage tool filters `state.json` by `category` and `is_outdated`.
See `@docs/pipeline.md` for the full pipeline architecture and stage handoff contract.

## Key Concepts Quick Reference

| Term | Definition |
|---|---|
| **Probe** | Implementation that fetches latest version from one upstream source type |
| **Probe Engine** | Runtime that loads TOML config, instantiates probes, merges with scanner results |
| **Probe Factory** | Maps `probe_type` string (from TOML) to the correct Probe class |
| **Probe Definition** | One `[[probes]]` entry in TOML with flat `args.*` fields |
| **ScriptProbe** | Escape hatch — runs a custom shell command for tools that fit no standard probe |
| **Auto-discovered** | Tools found by scanning the system (apt, snap, nvm, npm, docker, pm2, systemd) |
| **Registered** | Tools explicitly defined in `server-lens.toml` under `[[probes]]` — the interest list |
| **Untracked** | Tool found on system but absent from TOML — current version shown, no latest |
| **Display mode** | Default `server-lens` — instant render from SQLite, zero network, safe for MOTD |
| **Scan mode** | `server-lens scan` — full probe run, writes SQLite, emits events, fires webhooks |
| **VersionEntry** | Core data unit — one item in JSON output (see `@docs/data-schema.md`) |
| **state.json** | Saved `--json` output — shared state contract for downstream pipeline stages |
| **Event** | Structured diff result emitted after comparing current scan vs last SQLite snapshot |
| **Theme** | Named color token set — `claude` (orange), `claude-blue`, or `custom` — loaded from TOML `[theme]` |
| **Color Token** | Semantic color name (`accent`, `error`, `muted`, etc.) used in all UI components — never raw hex |
| **MCP Tool** | A callable function exposed to AI agents — e.g. `scan_now`, `get_outdated`, `create_schedule` |
| **MCP Resource** | A readable data URI exposed to AI agents — e.g. `tools://outdated`, `events://recent` |
| **MCP Prompt** | A pre-built agent workflow template — composes multiple tool calls into a structured output |
| **Schedule Entry** | A scan schedule stored in SQLite — either `one-time` (ISO 8601 datetime) or `cron` (expression) |
| **Scan Job** | An async scan triggered via API — tracked by `job_id`, polled via `GET /api/scan/status` |
| **TOML bootstrap schedule** | `[settings].scan_schedule` cron — used only if no SQLite schedule entries exist |

## Agent Rules

- **Adding a tool to track:** Edit `server-lens.toml` only — add a `[[probes]]` entry with flat `args.*` fields. No code changes needed.
- **Adding a new upstream source type:** Create `src/probes/XyzProbe.ts`, register in `src/engine/probe-factory.ts`. No other changes.
- **Schema changes:** `VersionEntry` and `Event` types in `src/schema/types.ts` are public contracts. Any field rename or removal requires updating `@docs/data-schema.md` and all downstream consumers.
- **UI is fully decoupled:** `src/ui/` only imports from `src/schema/types.ts`. Never import db or probe modules in UI components.
- **DB migrations:** All SQLite schema changes go through the migration runner in `src/db/database.ts`. Never alter tables directly.
- **Config is read-only at runtime:** `server-lens.toml` is never written to by the tool. Runtime state goes to SQLite only.
- **Webhook dispatcher is fire-and-continue:** Failed webhook delivery must not block or fail a scan. Log to `webhooks_log` and move on.
- **Display mode must be instant:** The default `server-lens` command (display mode) must never make network calls or run probes. It only reads SQLite.
- **Scan schedule has no default:** `[settings].scan_schedule` in TOML must be explicitly set. The tool must error clearly if scan mode is run without it configured.
- **API auth guard:** If `[api].host` is anything other than `127.0.0.1`, the server must refuse to start unless `[api].token` is set in TOML. Never expose an unauthenticated API to the network.
- **Scan job is async:** `POST /api/scan` must never block. It spawns the scan process, returns a `job_id` immediately, and the caller polls `GET /api/scan/status`. Only one scan may run at a time — concurrent `POST /api/scan` calls return `409 Conflict`.
- **TOML schedule is bootstrap only:** `[settings].scan_schedule` is read on first run and seeded into the SQLite `schedules` table if no entries exist. After that, the scheduler reads only from SQLite. TOML value is not re-read on subsequent starts unless the DB is empty.
- **MCP and REST share the same DB repos:** Never write separate DB query logic for MCP tools. Always import from `src/db/*-repo.ts`. See `@docs/mcp.md`.
- **stdio transport is stdout-silent:** In `server-lens mcp` mode, all logging goes to stderr only. Any stray stdout output breaks the MCP protocol and crashes the agent connection.
- **One scan lock, shared across MCP and REST:** `scan_now` (MCP) and `POST /api/scan` (REST) share the same process-wide scan lock. Concurrent triggers return the existing job_id.
- **UI uses theme tokens only:** Components in `src/ui/` must never hardcode hex color values. Always use `useTheme()` and reference semantic tokens (`theme.accent`, `theme.error`, etc.). See `@docs/ui-design.md`.
- **Status always uses symbol + color together:** Never convey status by color alone — always pair with a symbol from the approved symbol set.
- **`apt` category collapses by default:** Too many packages to show expanded. Show count summary header only; expand on user keypress.
- **Display mode renders instantly:** No spinner, no loading state, no async work in display mode.
- **Release notes are always null in default mode:** `release_notes` and `release_notes_source` must only be populated when `--with-notes` is explicitly passed. Never fetch changelogs during a cron scan or display mode render.
